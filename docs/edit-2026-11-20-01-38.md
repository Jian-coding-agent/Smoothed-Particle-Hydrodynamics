# 2026-11-20 — A3 lean solid list and a multi-GPU domain decomposition (D1)

Machine: KMG-XI, 8 × RTX 5090 D (32 GB, `sm_120`, 170 SM), driver 610.88, Windows 11.
Toolchain: CUDA 13.5 (portable PyPI-wheel install, no admin), MSVC 19.29 (VS 2019),
CMake 4.4.5 + Ninja. All numbers below were measured on this machine.

The RTX 5090 D is a 1/64-rate fp64 part, so all timings are for the fp64 path unless stated
otherwise.

## 1. A3 lean solid list (A6)

The static solid/solid pair list used to store, per pair, the partner index plus three
pre-computed weight vectors (`sG`, `sB`, `sD`, 9 `Real` = 88 B/pair). It now stores only the
partner index (4 B/pair) and rebuilds the weights from the static `solidPack` every step.

The rebuild duplicates `k_solid_pair_fill`'s arithmetic operand for operand and in the same
order, so both layouts are **bit-identical** (`result1.sphbin` SHA-256 equal, fp64 and fp32,
checked over 501 steps on the 1 203 508-particle deck).

| | fat | lean |
|---|---:|---:|
| A3 list, 188 k solids / 14.86 M pairs | 1 254 MB (6.95 KB/solid) | **66 MB (0.35 KB/solid)** |
| peak VRAM, 1203k deck | 2 999 MiB | **1 811 MiB** |
| fp64 | 11.31 ms/step | 13.43 ms/step (+18.7 %) |
| fp32 | 2.90 ms/step | 3.87 ms/step (+33 %) |

The surcharge is addressing: the fat list is slot-major (a warp reads 32 consecutive slots),
the lean one gathers `solidPack` at the partner's index (two cache lines per visit, random).

Selection is automatic: `auto` keeps the fat list until it would exceed `SPH_A3_LIMIT_MB`
(default 4096 MB) and switches to lean above that, so small decks keep full speed and only
10^7-particle decks pay the surcharge. Because the two layouts are bit-identical the choice
never changes the output.

## 2. D1: domain decomposition across the 8 GPUs

`SPH_RANKS=K` runs K host threads, one CUDA device each, on a decomposition that is chosen
automatically. Single GPU (no `SPH_RANKS`) is unchanged.

### 2.1 Partitioning

* Each particle gets a compute weight: **fluid 1.0, solid 0.5, wall 0.0**. 38 % of this deck
  is wall, which runs no per-step kernel at all (it is only read as a neighbour), so balancing
  by particle count leaves whole ranks idle.
* The deck is sorted per axis and cut at equal cumulative weight: along x, then along y inside
  each x slab, then along z. A cut is never placed inside a group of equal coordinate, so each
  rank owns a **rectangular box**.
* Every ordered factorisation `nx*ny*nz == K` is evaluated against the real coordinates and
  the one minimising `max_r(own_weight + ghost_weight)` wins (ties: fewer ghosts).
  On the 1203k deck K=8 picks **2×2×2** (170 244 ghost slots, **14.1 %**) where the 1-D
  `8×1×1` needs 464 580 (38.6 %). On the synthetic 9.6 M deck the copies are separated by
  0.05 m gaps, so it picks `8×1×1` with **zero** ghosts.
* Ghost set: every particle inside the rank's box expanded by `3*hsml` on every face that is
  not owned. Complete by construction: for a neighbour `q` of an owned `p`, `|x_q - x_p| < 3h`
  puts `q` inside the expanded box on each axis.

### 2.2 What each rank computes

Owned particles live in `[0, num)` in the deck's order (`fluid | solid | wall`); ghosts are
appended in `[num, numP)`. Every process loop is bounded by the owned counts, so ghosts are
read-only and there is no write race with their owner. `Pia` and `solidPack` are indexed by
`q - ntotal` with `numP - ntotal` slots, so ghost solids get real slots and no index remapping
is needed in the kernels.

### 2.3 Exchange (three points per step)

```
k_prepare                                  (p, irho, SurFD for owned particles)
  E1: x, vx, rho, p, SurFD, PIJW  [+ Pia[12] for solids]   12 / 24 doubles
cell hist/scan/scatter/sort -> pass1 -> constitution
  E2: rho, Pia[12] for solids                              13 doubles
pass2_fluid
  E3: PIJW for fluids                                      3 doubles
pass2_solid -> update
```

Transport: one gather kernel per record group, **one** D2H of a whole per-rank pinned block,
a barrier, a CPU memcpy relay of each peer's block into the rank's receive block, **one** H2D,
one scatter kernel, a second barrier. This replaced one `cudaMemcpyAsync` per (peer, direction),
which costs ~150 µs each on Windows/WDDM — 21 copies/step at K=8 for 2.2 MB of data.

`irho` is not exchanged: it is rebuilt on the ghost block with `k_prepare`'s exact expression.
The barrier is adaptive (short spin, then block), switchable with `SPH_BARRIER=spin|block`.

### 2.4 Repartition and migration

`SPH_D1_REPART=N` repartitions every N steps, after the result write:
each rank publishes its owned dynamic state, rank 0 rebuilds the cuts from the **current**
positions (same grid unless `SPH_D1_REGRID=1`), ranks rebuild their decks, and owned state is
moved (20 doubles per particle: `x, vx, rho, SurF, A, vecn`; the rest is static from the deck
or recomputed before its next use). `solidPack`, the A3 list, the cell grid and the exchange
links are rebuilt.

Cost at K=8 on the 1203k deck: **820 ms per event** (N=500 on a 3001-step run: +1.6 ms/step,
+30 %). The two known optimisations (build the A3 list once globally and slice it; keep fixed
cut coordinates instead of re-sorting) should bring this to ~250–300 ms.

## 3. Validation

Cross-machine acceptance criterion used throughout: `x/y/z` identical or ≤1e-9 m, fluid `p`
≤1e-3 Pa, solid `trace(Pia)` ≤1e-3 Pa. Result files store `x y z ppp`
(`ppp` = `p` for fluid, `Pia11+Pia22+Pia33` for solids, 0 for walls), so `vx` is not in the
file; the velocity agreement was not measured directly, but positions after 501 steps differ by
at most 2.2e-16 m, which bounds the velocity difference far below 1e-9 m/s.

| case | result |
|---|---|
| single GPU, 1203k, 501 steps | `D80E092EEE85CBCF…`, 11.287 ms/step (unchanged before/after this work) |
| `SPH_RANKS=1` | **byte-identical** to single GPU |
| `SPH_RANKS=1` + `SPH_D1_REPART=100` (4 events) | **byte-identical** to single GPU |
| `SPH_RANKS=8`, 1203k | x/y/z ≤ 2.2e-16 m, fluid p ≤ 2.6e-10 Pa, solid trace ≤ 1.2e-7 Pa |
| `SPH_RANKS=8` + `SPH_D1_REPART=100`, 1203k | x/y/z ≤ 1.1e-16 m, fluid p ≤ 2.6e-10 Pa, solid trace ≤ 1.2e-7 Pa |
| `SPH_RANKS=8` + `SPH_D1_REPART=500`, **3001 steps** | x/y/z ≤ 1.9e-10 m, fluid p ≤ 2.2e-5 Pa |
| fp32 single GPU | `E50ACB1D…`, unchanged |

`git diff` of this change touches only `cuda/src/{sph.h,sph_host.cu,sph_kernels.cu}` and
`cuda/README.md`.

## 4. Performance

### 1203k deck (the current case)

| K | split | ms/step | speedup | ghost slots |
|---:|---|---:|---:|---:|
| 1 | — | 11.3 | 1.00× | — |
| 2 | 1×2×1 | 7.87 | 1.44× | 42 396 (3.5 %) |
| 4 | 1×2×2 | 6.40 | 1.77× | 100 076 (8.3 %) |
| 8 | 2×2×2 | 3.4–4.7 | **2.4–3.2×** | 170 244 (14.1 %) |

The K=8 spread is the machine, not the code: GPU 0 and GPU 4 also drive the desktop and the
slowest rank gates every barrier (the K=8 run is deterministic — identical hash on repeats).
Phase split at K=8: `pass1_fluid` 1.6 ms, E1 0.58–1.11, E2 0.22–0.58, E3 0.35, cell list 0.3,
barriers 0.1–1.5. Each exchange point has a hard floor of ~0.4–0.7 ms (one D2H + one H2D + two
kernels + two host barriers) that barely depends on the payload — E3 moves 3 doubles and costs
as much as E1. That floor is why 8 GPUs only buy ~3× on a 1.2 M-particle case, where each rank
has just 1.6 ms of compute per step.

### Synthetic large decks (replicating the 1203k deck R times along x, lean solid list)

| deck | particles | K | split | ms/step | speedup | peak VRAM |
|---|---:|---:|---|---:|---:|---:|
| 8× | 9 628 064 | 1 | — | 100.1 | — | 11.3 GB |
| 8× | 9 628 064 | 8 | 8×1×1 (zero ghosts) | **14.13** | **7.08×** | 1.82 GB/GPU |
| 8× | 9 628 064 | 8 | 2×2×2 (forced) | **23.03** | **4.35×** | — |
| 16× | 19 256 128 | 1 | — | 201.1 | — | 22.1 GB |
| 16× | 19 256 128 | 8 | 8×1×1 | 28.60 | 7.03× | 3.19 GB/GPU |

Both large-deck comparisons match the single-GPU run within the same criterion
(9.6 M: x/y/z ≤ 3.6e-15 m, fluid p 5.2e-10 Pa; 19.3 M: ≤ 7.1e-15 m, 5.2e-10 Pa).

**Read these numbers with the caveat they need.** The 7.08× / 7.03× figures are the best case
for the synthetic input: the replicated copies are separated by 0.05 m gaps, so the partitioner
legitimately aligns eight slabs with the eight copies and the ghost set is empty — no exchange
at all. The honest "with halo exchange" number on the same 9.6 M deck is **4.35×** (forced
2×2×2). What the large decks do show is the amortisation: per-rank compute grows from 1.6 ms to
9–10 ms while the exchange points stay put, so the exchange share of the step falls from 37 %
to 28 % and the speedup rises from ~3× to ~4.4×.

Single-GPU feasibility after A6: 19.3 M particles need **22.1 GB** (72 % of a 32 GB card) and
201 ms/step; K=8 drops that to 3.19 GB/rank and 28.6 ms/step.

## 5. Limits and what to do next

* **No P2P on this box.** `cudaDeviceCanAccessPeer` is 0 for every pair (consumer cards, mixed
  root complexes), so all halo traffic is host-staged at ~20 GB/s aggregate. GPU 0 is on a
  PCIe Gen2 slot; the other seven are Gen5.
* **The 1.2 M case is exchange-latency bound**, not compute bound. More GPUs will not help it
  much; merging exchange points or overlapping E1/E3 with the cell-list build is the way in.
* **Repartition cost** (820 ms/event at K=8) is dominated by the per-rank A3 rebuild (~0.15 s
  each) and the serial rank-0 layout; both have a clear fix, see §2.4.
* **fp32 is not supported** on the D1 path (refused with a clear message). fp64 is the only
  path that matters at 10^7 particles.
* `SPH_PROFILE` / `SPH_BENCH` are not implemented on the D1 path; `SPH_D1PROF=1` prints the
  per-phase table and the exchange split instead.

## 6. Environment variables added

| variable | effect |
|---|---|
| `SPH_A3_FULL=0|1` | force the lean / fat solid list (unset = auto) |
| `SPH_A3_LIMIT_MB` | auto threshold for the solid list (default 4096) |
| `SPH_RANKS=K` | run K ranks on K devices (unset / 1 = single GPU) |
| `SPH_RANKS_GPUS=0,1,…` | which devices the ranks use (default `0..K-1`) |
| `SPH_D1_REPART=N` | repartition every N steps (default 0 = never) |
| `SPH_D1_REGRID=1` | also re-search the block grid at a repartition |
| `SPH_D1_SPLIT=nx,ny,nz` | force one candidate decomposition |
| `SPH_D1PROF=1` | per-phase timing plus the exchange split |
| `SPH_BARRIER=spin|block` | barrier flavour (default adaptive) |

Example:

```
set SPH_MAXSTEP=3001
set SPH_RANKS=8
set SPH_D1_REPART=500
cuda\build\sph_cuda.exe _local\cases\input_8x1203k.sphbin --fp64
```

## 7. Bugs fixed on the way

* `eta`/`SurFD` pairing used the local index; with ghosts appended a left ghost could win the
  `p > q` comparison and flip `eta` by 50× on surface-crossing pairs. It now uses the deck
  index (`sph_pair_hi`), which is a no-op on single GPU.
* `build_cells_for(s)` histogrammed from `s` but scattered with the live `g.x`. Start-up masked
  it (`x == X0`); after the first repartition the A3 list drifted (79.0 → 70.4 pairs/solid,
  ELL width 92 → 118) and became non-deterministic. With `launch_cell_scatter(s, …)` the list
  is exactly 14 858 832 pairs / width 92 at every repartition.
* `nblocks(0)` launched `<<<0, 256>>>` (invalid configuration) for a rank that owns no solid;
  both `launch_build_solid_pack` and the `nblocks` helper were fixed.
* `finish_deck` compared the owned row count against the full row vector, so any rank with
  ghosts refused to load.
