## 1. V2: K > 1 is byte-identical to K = 1

The decomposition used to differ from the single-GPU run at the 1e-16 level, because each
rank derived its own neighbour grid from its own rows and ordered a cell by *local* index —
and a local index says nothing about the deck order once ghost slots are appended.

Two changes make the summation order the one the single-GPU run uses:

* every rank bins into the **global grid** derived once from the whole deck, and that grid
  stays fixed for the run (it no longer drifts when a repartition re-derives it);
* `k_cell_sort` orders a cell by **global id** (`s.gid`); with a single rank `gid` is null
  and the local index *is* the global one, so the two cases agree by construction.

The payoff is a test, not a number: a halo or exchange bug can no longer hide under rounding
noise.  Everything below was checked with `fc /b` on the result files, not with a tolerance.

| configuration | result |
|---|---|
| K = 2, 4, 8, 501 and 3001 steps | byte-identical to K = 1 |
| K = 8, 3001 steps, six automatic halo rebuilds | byte-identical |
| K = 8, 3001 steps, `SPH_D1_REPART=1000` | byte-identical |
| `SPH_RANKS=auto`, 501 steps | byte-identical |
| **negative control**: K = 8, `SPH_D1_SKIN=0`, 3001 steps | 2.0e-6 m / 1.7 Pa off |

The negative control is what makes the rest meaningful: with the skin disabled the
decomposed run still decays, so the byte-identity check is able to fail.

## 2. P10, P11, P13, P14

| id | what was done | effect |
|---|---|---|
| P10 | the send block is double buffered and consecutive exchange points alternate halves, so the trailing barrier is unnecessary (a rank can only rewrite a half after the *next* exchange's barrier, which no rank reaches before finishing its relay) | two barriers per exchange point → one; six per step → **one** |
| P11 | the ghost solids come in two layers: layer 1 is what the block box selects and **runs its own constitution** (`pass1_solid` + `constitution` over slots `[0, solnum + ngs1)`), layer 2 is layer 1's A3 partners in the reference configuration, which are only ever read | **E2 is gone** — one exchange point per step.  Costs ~1 790–3 300 extra ghost solids per rank on this deck and ~25 % more solid work in the halo |
| P13 | `Pia` / `solidPack` hold one slot per *solid* (owned, then ghost) instead of one per index ≥ `ntotal`; walls and ghost fluids take no slot | 92 MiB on the 1203k deck, 1.47 GiB on the 19.3 M one, ~13 MB per rank here |
| P14 | two result staging buffers and a writer thread on rank 0; a stage is reused two results later and rank 0 waits for that writer before the barrier that releases it | the 55 ms file write no longer stalls every rank |

P11 is the structural one.  A layer-1 ghost has to produce the *same bits* as its owner, which
works because the A3 partner scan uses the same global grid and the same global-id order on
both sides, so the partner set and its order are identical.  That is exactly what the byte
identity table above measures.

## 3. L1 / L2 / L3: choosing K, and what a ghost costs

`SPH_RANKS=auto` first ranks the devices — a 64 MB device-to-device bandwidth probe, free
memory, and the display-watchdog flag, which is how a card that drives the desktop gets
demoted — and then chooses K from the *actual* partition: for every K it runs the same search
`build_job` runs and predicts

    T(K) = max_r(own weight) + w_ghost · ghosts/K + XCH_UNITS

i.e. the slowest rank's compute plus its share of the ghosts plus one exchange point's floor.
The smallest K within `SPH_D1_AUTO_SLACK` (default 10 %) wins, so a batch of cases keeps cards
free.  On this machine all eight cards carry the display flag, so the ranking falls back to
bandwidth, the model picks K = 8, and the run is byte-identical to K = 1.

L2/L3 changed the objective: a solid particle weighs 0.45 (the measured 0.41 with the fat list
and 0.97 with the lean one, so the default sits between and is a knob), and a ghost is charged
0.06 instead of a full particle — it is a cell-list slot plus its share of the exchange, not a
particle that computes.  Charging a ghost at the owned rate, as before, turned the ghost term
into an exchange penalty with an arbitrary scale.

## 4. M8: the reflection at z = 1

`k_update_fluid()` flipped `v_z` whenever `z > 1.0`, which also flips a particle that is
already moving down and can leave it oscillating just above the plane.  The standard form
reflects only outward motion and is now the default; `SPH_REFLECT=flip` keeps 1.cpp's literal
behaviour.  The fluid in `input.dat` stays below 0.45 m, so the two settings produce identical
results on it — verified, not assumed.

## 5. C9 follow-up: the displacement readback

The halo trigger reads an 8-byte device value back to the host, and a synchronous readback
costs ~0.6 ms on Windows/WDDM — a quarter of the step.  The reduce still runs every step, but
the readback is scheduled from the measured rate so that at most 10 % of the skin can go
unseen; it costs ~0.01 ms/step.  On this deck the interval settles at 64 steps.

## 6. Performance

### 6.1 What the exchange costs now

Counted from the actual ghost sets of a K = 8 run (2×2×2, 237 298 particles), summed over the
eight ranks:

| | before | after |
|---|---:|---:|
| ghost fluids / solids | 67 214 / 14 260 | 67 878 / 24 170 |
| exchange bytes per step | **11.72 MB** | **5.43 MB** (−54 %) |
| exchange points | 3 | **1** |
| host↔device copies per step | 6 | **2** |
| rank barriers | 6 | **1** |
| record sizes | fluid 12, solid 24, E2 13, E3 3 doubles | fluid 8, solid 7 |

The ghost set grew ~13 % (the C9 skin, and P11's second layer): 102 602 → 113 176 slots,
duplicate rate 43.2 % → 47.7 %.  So the −54 % is achieved *despite* more ghosts; on the same
ghost set the record change alone is −58 %.

### 6.2 Step time

Same-contention, back-to-back comparison (`SPH_D1PROF`, both binaries at the same moment,
K = 8, 101 steps): the previous build 10.715 ms/step, the new one 10.651 — a wash, but that
new build still carried the per-step displacement readback (0.607 ms in its phase table),
which is now ~0.01 ms.  Net: about **−6 %** at this size.

Absolute numbers from an idle window, for scale (different minutes, same binary except where
stated; only same-window pairs are meaningful on this shared machine):

| K = 8, 237k | ms/step |
|---|---:|
| original exchange (12/24 + E2 + E3) | 2.396 |
| P8/P9 only (8/7, no E3), no skin | 2.134 |
| P8/P9 with the 1.5 h skin | 2.388 |
| final (skin + P10 + P11 + P14) | ~2.2–2.4 |

Single GPU is unchanged: `K = 1` output is byte-identical to the previous build, and the
single-GPU path costs the same 3.25 ms/step on 237k (P13 only frees memory).

So at 237k the change is performance-neutral to slightly positive: P8/P9 bought 11 %, the skin
and P11's halo work cost most of it back, and the adaptive readback recovers a few percent.
The exchange structure is much lighter, but on a 237k deck the exchange is only ~28 % of the
step, so there was not much to win.

### 6.3 The 19.3 M caveat — this is where it gets slower

The numbers from `docs/edit-2026-11-20-01-38.md` sec. 4, measured on this machine when idle:

| deck | particles | K | split | ms/step | speedup |
|---|---:|---:|---|---:|---:|
| 16×1203k | 19 256 128 | 1 | — | 201.1 | — |
| 16×1203k | 19 256 128 | 8 | 8×1×1 (no ghosts) | 28.60 | 7.03× |
| 8×1203k | 9 628 064 | 8 | 2×2×2 (real halo) | 23.03 | 4.35× |

Those are *before* this work.  With a real halo the 19.3 M case is ~45–50 ms/step by the
9.6 M ratio.

**C9's rebuild cost scales linearly with the particle count and was not dealt with here.**
Measured on 237k: 175 ms per rebuild before P11, 260 ms after (layer-1 ghosts run their own
constitution too) — that is 0.74–1.1 µs per particle.  At 19.3 M a rebuild is therefore
**14–21 s**, and the default 1.5 h skin fires roughly every 700 steps, so it amortises to
**20–30 ms/step** on top of 28.6 ms/step.  The decomposed 19.3 M case is likely about twice as
slow as it was, and that is a regression introduced by the C9 fix, not by P10–P14.

Two ways out, neither implemented yet:

1. **scale the skin with the deck**: solve for s such that the amortised rebuild is ≤5 % of the
   step.  With this case's displacement rate (~1e-5 m/step) s ≈ 6 h = 6 cm gives a ~3000-step
   interval and 5–7 ms/step, at the cost of a wider ghost band (3h + 6h) and the memory and
   cell-list work that implies;
2. **make the rebuild cheap**: `build_ranks` / `make_part` select ghosts with serial
   O(num·K) host loops on rank 0, which is what dominates the 14–21 s.  Parallelising that
   (one pass per rank thread, or an incremental update restricted to the moved particles)
   should take an order of magnitude off.

## 7. Why there are no fresh 19.3 M numbers in this note

The box is shared and another project's workload (`sim_fvm_hllc_gpu.exe`, a 1 895-scenario HLLC
sweep, 24 workers, three per GPU) was running for the whole window in which these numbers
should have been taken.  With it running, the same 237k deck measures 5.7–20.3 ms/step in
different attempts against 3.25 ms/step idle — a 1.8–5.6× inflation — so a 19.3 M measurement
would have been meaningless.  The 19.3 M rows above are quoted from the previous session's log,
which was taken on this machine when idle.

## 8. Reproducing

```bat
cd cuda && build.bat                 :: or the CMake/Ninja recipe with the local CUDA 13.5
set SPH_MAXSTEP=1001
set SPH_RANKS=8
set SPH_D1PROF=1
build\sph_cuda.exe ..\input.dat
```

`SPH_D1PROF` prints the per-phase and per-exchange-point split.  To check the byte identity:

```bat
fc /b result1.sphbin <single-GPU run>\result1.sphbin
```

The model-facing knobs are `SPH_D1_SKIN`, `SPH_D1_W_SOLID`, `SPH_D1_W_GHOST`,
`SPH_D1_XCH_UNITS`, `SPH_D1_AUTO_SLACK`; see `cuda/README.md`.
